# Three hardware recordings and upstream update, 2026-10-18

The three recordings are in the repository's `scratch/` directory. The user
reports that the repeated build/capture cycle is becoming tiresome and asks
whether the evidence explains why no OS boots. **It does not yet establish
a shared boot cause.** The earlier `$408253CC` pointer fault was too narrow
to define the broader investigation. No further overlay change or hardware
capture is requested on this evidence.

## Recordings

All three recordings are 1920x1080 at 60 fps. Overlay fields were sampled at
10 fps using the exact glyphs from the RTL. MiSTer OSD menus cover the lower
pointer rows in some frames; those occluded readings are excluded. The
checkout is `2aaf9ab`; this is not a verified fitted-artifact identity.

The second clip's `$0545` event is an ATC fault on a **word read**, supervisor
data. An earlier commentary called it a write; that was a decoding mistake.
The original `$B6DB6DB6` case was a longword bus read at a different PC.
Neither address by itself distinguishes a wrong register/EA, stale data,
corrupted software state, or an invalid mapping. The new pointer capture did
not fire in these clips, so it supplied no pointer provenance.

Decoded frames, contact sheets, and transition logs are under
`scratch/ap68040_diag/hardware_20261018/`. Snapshot display/extraction latency
makes the listed transition times approximate.

## Upstream integrated

Fetched `origin/faster` in the reference `AP68040` checkout and confirmed
`a171fdfe87a6eb192d8840f9bc4d7186e587dcae`. Imported both changes since the
previous pin `ab4d83d`:

* `8c778ee`: underflow denormalization uses the unrounded exponent; UNFL's
  saved intermediate state retains that exponent.
* `a171fdf`: enabled arithmetic exceptions pend until the next FPU
  instruction; store exceptions and FSAVE frame contents are corrected.

The import includes their backend/MMU timing changes, documentation, and
`t_fpexc`. Q800's local RAM implementation and diagnostic exports are
preserved. These are real upstream corrections; the videos do not establish
that either correction causes or fixes the boot failures.

Validation: 40/40 selected upstream runs pass (eight programs, five bus
configurations): `t_fpexc`, `t_fpu`, `t_fpu_frames`, `t_fpu_resume`, `t_mmu`,
`t_cache2`, `t_movem_restart`, and `t_stld`. Q800's native adapter regression
passes fixed/random latency at 3,093/4,121 clocks. Platform lint passes with
existing warnings.

## Replace narrow capture iterations with short platform tests

`python3 scripts/test_ap68040_platform.py` under WSL now runs short programs
through the native CPU, **actual** `quadra800` service logic and
`wombat_bus32`, `sdram_beat32`, `sdram.sv`, and the protocol-checked SDRAM chip
model. ROM is a fixed-latency stand-in for DDR3. The test uses the normal ROM
reset/overlay path; upstream programs enter RAM through a ROM trampoline.
The chip model's storage is flattened solely for loading the test programs.

| Upstream `t_fpexc` | 8,583 | Pass, zero SDRAM protocol errors |
| Upstream `t_fpu` | 108,921 | Pass, zero SDRAM protocol errors |
| Upstream `t_stld` | 402,936 | Pass, zero SDRAM protocol errors |

Each execution takes under two seconds after compilation. The first scratch
fixture incorrectly relied on forcing the boot overlay off; Verilator did
not hold that force, so reset fetched empty ROM. That was fixture setup,
not an integration defect. The checked-in test uses normal ROM startup and
does not force internal CPU/machine state.

These tests improve coverage over the adapter's ideal memory array. They
still use portable CPU RAMs rather than the fitted Intel primitives, have
no disk/HPS traffic or external interrupt workload, and do not boot an OS.
They therefore do not close the remaining boot-device I/O, MMU-state, or
exception-recovery questions. The established RAM/ROM path passing these
programs is useful negative evidence, not proof that the complete integration
is correct. Future directed reproductions should run here where applicable
before asking the user to build another hardware artifact.

The existing 04:00 TimeQuest report was inspected read-only. Its listed clock
domains have nonnegative setup/hold slack and no unconstrained clocks. This
does not validate unconstrained I/O paths or identify the actual loaded
artifact. No Quartus process, full-machine OS boot simulation, deployment,
or hardware reset was started.
